An agent is a loop, not a single call

Every turn: the context (instructions, tools, history) goes to the model, it thinks, acts through a tool, observes the result, and the harness checks whether to stop. The result is appended to the context and the loop runs again.

Why does the second turn cost more than the first?

The whole context is re-sent on every model call, and it grew by the first tool result. Cost per turn rises as the conversation grows, so long agent runs need compaction and output limits.

Where in the loop should a write action like a refund be stopped for approval?

Between Act and the real side effect: a gate in the harness holds the tool call, a human approves, then it executes. The model never decides alone on irreversible actions.

The harness: guides, gates, sensors

Guides steer before the agent acts: the spec, system prompt and tool descriptions. Gates allow or deny an action: permissions, read-only files, approvals. Sensors watch what happened and react: tests, PII scanners, cost and attempt limits.

Why is "make the tests pass" a dangerous instruction without a gate?

The shortest path to green is editing the test: changing an expected value or deleting an assertion. Making spec-owned test files read-only to the agent removes that path.

Which guard here is a distributed-systems idea, not an AI idea?

The idempotency key on write tools. Agents retry after timeouts exactly like queue consumers redeliver, so every write tool needs deduplication. That is Lab 1 in a new setting.

Self-fixing loops: green is not the same as correct

Spec-driven development: a markdown spec, an agent that generates code, tests that judge it, and a loop that feeds failures back until green or until the attempt limit escalates to a human.

Recall from memory

What two things in the spec stop most fake greens?

Acceptance criteria written as tests for every state and edge case, and a rule that those tests are owned by the spec and cannot be changed by the agent.

Why have a maximum number of attempts at all?

Each attempt re-sends a growing context, so cost climbs per attempt, and an agent stuck on the same failure rarely recovers. Escalating to a human early is cheaper and safer.

Recall from memory

Why does judge noise pull every model toward 50%?

A flipped verdict turns passes into fails and fails into passes. A strong model loses more than it gains, a weak one gains more than it loses, so observed scores shrink toward the middle and the gap between models narrows.

Name two ways to make a release gate trustworthy.

Average several runs and gate on the mean with its spread, and reduce judge noise with exact-match or rule checks where possible, keeping the LLM judge for what truly needs judgment.

Agents retry, and retries double-charge

200 support sessions each owe one £42 refund. The refund runs, but sometimes the response times out, so the agent cannot tell it worked and calls the tool again. This is Lab 1's duplicate delivery, caused by an agent.

Recall from memory

Why not just set retries to zero?

Then every real timeout leaves the customer unsure whether they were refunded, and real failures are never recovered. Retries are needed; they must be made safe with an idempotency key.

Where should the key come from: the model or the harness?

The harness, derived from the business action (for example the order ID). A model can invent a new key on every retry, which defeats the deduplication.

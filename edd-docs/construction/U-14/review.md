## Checks with no finding
- **Rewrites (focus 2):** both rules are in `beforeFiles`. Next's loader confirms they are compiled as `beforeFiles`, so they win over the prerendered `/play/[slug]` page when `SLUICE_ORIGIN` is set. `/play/sluice/:path*` also matches `/play/sluice` (path-to-regexp makes `/:path*` optional), so the root rule is redundant but is required verbatim by PROJ-AC-04 and harmless. `/play/sluicex` and `/play/sluice-lab` do not match. With the origin unset, the page is the only answer, `dynamicParams = false`, and other slugs are 404.
- **Header ordering (focus 3):** the play rules come after the baseline and site rules. On the real loader output, no site source matches `/play/*`. The play sources match only `/play/<slug>` and below. `security-headers.test.mjs` proves on compiled matchers that none of the 8 `SITE_PATHS` gets `'wasm-unsafe-eval'` when deployed, and that `/terminal`, `/api/analytics`, 404 and the others keep the exact baseline CSP. While the demo is not deployed, the fallback page gets exactly the site CSP (needed for its RSC inline script). Baseline HSTS, XFO, COOP and Permissions-Policy still apply to `/play/*`.
- **Headers on proxied responses:** `next.config` headers are emitted as `continue` routes ahead of rewrites in Vercel's routing, so they apply to the external rewrite. What happens when the zone sends a same-named header is not testable here: a local zone stub cannot be used because `playOrigin` requires https. This is already listed in `projects-plan.md` Risks. Carry it into U-16's owner checklist as a `curl -I https://<preview>/play/sluice` check (CSP equals `zoneCsp`, `X-Robots-Tag: noindex`).
- **Zone CSP sufficiency (focus 3):** `'wasm-unsafe-eval'` covers `WebAssembly.instantiateStreaming`. `connect-src 'self'` covers fetching the `.wasm` file and the recorded examples. `worker-src 'self'` covers same-origin module workers (blob workers would be blocked, which is intended). `base-uri 'none'` is fine because Vite emits no `<base>`. Vite production output has no inline script.
- **buildEnv snapshot (focus 1):** this is correct. Next calls `loadEnvConfig` before evaluating the config, so `.env*` values are in the snapshot. On Vercel the env is read once per build and baked into `routes-manifest.json`, so a changed origin needs a redeploy, which the contract states (line 18). The snapshot is a module constant, not a `nextConfig` property, so it is not serialized into `required-server-files.json`. It also keeps `rewrites()` and `headers()` consistent with each other and with the test harness, which restores `process.env` before calling them.
- **Validation fails closed:** a bad origin throws from both `rewrites()` and `headers()`, and the Next loader propagates it, so the build fails. Uppercase hosts, userinfo, IDN, path, query and hash are all rejected through the `url.origin !== value` comparison.
- **Tests (focus 5):** none is vacuous. PROJ-AC-03/04 deep-equal the rules. PROJ-AC-02 has a negative `it.each` that names the env var. PROJ-AC-11/12 are checked on both source strings and compiled matchers. PROJ-AC-13 checks the h3 text, "formerly PromptShield", the "In progress" badge and the absent metric, plus a no-`formerName` negative. PROJ-AC-05 checks one `h1` by count, the repo link absent and present (`rel="noopener noreferrer"`), and unknown slugs 404. PROJ-AC-06 checks the 308 and the relative `Location` in e2e (not run by me) and in unit tests. The removed PromptShield "Proof of concept" test was moved onto a fixture, so HOME-AC-13 keeps its coverage.
- **Content (focus 6):** every new `work.ts` value cites P-01..P-04, P-08 or P-09. The `profile.ts` labels `formerly` and `Demo coming soon` appear verbatim in PROJ-AC-13/05. `repoUrl` is unset (P-07, private repo). `metric: null` (P-11). No target month (P-04). Nothing invented. No email anywhere in the diff (the PII and literals gates still need the gate run). `/terminal` is untouched. `posts.ts:25` (F-60) still says "Measuring PromptShield". That text is owner-confirmed; renaming it is the owner's call.
